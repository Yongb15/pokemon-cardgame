# 관리자 포인트 지급 — 설계

운영자가 특정 사용자에게 포인트를 **지급**한다(보상·이벤트·오류 보정). 차감은 하지 않는다. 처리방침·약관에는 이미 "운영자 포인트 조정"이 있고, 장부 종류 `admin_adjust`도 있다(지금은 미리보기 테스트 충전에만 쓰임).

사용자 결정(2026-10-13): 대상은 **회원 코드**로 지정, **지급만**, 한도 **1회 100,000P · 관리자당 하루 500,000P**.

## 1. 회원 코드
- `users.member_code` — 8자리 대문자 16진수(예: `7F3A9C21`, 화면에는 `7F3A-9C21`), **UNIQUE**, DB 기본값 `upper(encode(gen_random_bytes(4), 'hex'))`
  - 새 사용자: 가입 INSERT는 지금처럼 `nickname`만 넣고 코드는 기본값으로 채워짐(`api_rw`의 INSERT 권한은 그대로). 아주 드문 충돌(UNIQUE 위반)은 가입 트랜잭션을 한 번 다시 시도
  - 기존 사용자: 마이그레이션에서 소유자 계정이 채움(충돌 시 다시 생성하는 루프), 이후 NOT NULL
- **본인 마이페이지에만** 표시(복사 버튼, "운영자에게 포인트 지급이나 문의를 할 때 알려 주세요"). 경매·알림·공개 응답 어디에도 없음 — 경매별 익명(A-3)은 그대로
- 비밀이 아니라 **식별자**: 알아도 할 수 있는 건 "관리자가 그 사람에게 포인트를 주는 것"뿐. 그래도 관리자 조회는 분당 횟수 제한
- 바꾸기 기능은 없음(필요해지면 따로)

## 2. 지급 흐름 (`/admin` 의 새 섹션 "포인트 지급")
1. 관리자가 회원 코드 입력 → `GET /admin/members/:code` → `{ nickname, joinedAt, pseudonym }`
   - 닉네임은 **사용자가 함께 알려 준 닉네임과 맞는지 확인용**(관리자 화면에서만, 글자로 표시). 잔액·덱·컬렉션은 보여 주지 않음
   - `pseudonym`은 기존 관리자 전용 구분값(경매 화면과 같은 값) — 다중 계정 의심 시 대조용
   - 없는 코드 → 404(같은 "회원을 찾을 수 없어요")
2. 금액(1~100,000 정수)과 이유(1~200자, 필수, **개인정보 금지** 안내 문구) 입력 → 확인 대화상자("트레이너4868에게 10,000P를 지급할까요?") → `POST /admin/points/grant { code, amount, reason, idemKey }`
3. 결과: 성공(지급 후 잔액은 보여 주지 않고 "지급했어요"), 한도 초과 409, 자기 자신 403

## 3. 규칙
- 관리자 확인은 기존과 동일: 매 요청 세션 + `admins` + 로그인 12시간 이내, 아니면 **404**. 쓰기는 Origin 검사 + 분당 20회(기존 관리자 쓰기 제한 공유)
- **자기 자신에게 지급 불가**(이해 충돌, 경매 처리와 같은 원칙) → 403
- 1회 1~100,000P, **관리자별 한국 시각 하루 합계 ≤ 500,000P**
  - 합계는 `admin_point_grants`에서 그날(KST) 그 관리자의 금액 합. 경쟁을 막기 위해 트랜잭션 안에서 관리자 id로 `pg_advisory_xact_lock`(경매 개수 제한과 같은 방식) 후 합계 확인 → 지급
- 멱등: `idemKey`(8~64자) — 같은 키로 두 번 보내면 처음 결과를 그대로(장부의 `idem_key = 'admin-grant:' || idemKey` UNIQUE)
- 탈퇴한(또는 탈퇴 중인) 사용자: 코드가 없어지므로 404

## 4. 데이터 (마이그레이션 0022)
- `users.member_code text NOT NULL UNIQUE DEFAULT …` (+ 기존 행 채우기, CHECK `^[0-9A-F]{8}$`)
- `admin_point_grants(id uuid PK, admin_id → users ON DELETE SET NULL, user_id → users ON DELETE SET NULL, amount int CHECK 1..100000, reason text CHECK 1..200자, entry_id → point_entries, created_at)` — **추가만**(api_rw에 UPDATE·DELETE 없음). 탈퇴해도 기록은 남고 id만 비워짐(경매 기록과 같은 원칙)
- 장부: `point_entries` 한 줄 `kind = 'admin_adjust'`, `ref = 'grant'`, 잔액 갱신은 기존 `credit()` 경로(잠금 순서: 대상 포인트 계정 하나)
- 권한 `api_rw`: users.member_code SELECT, admin_point_grants SELECT·INSERT(admin_id, user_id, amount, reason, entry_id). 시작 시 권한 검사 목록과 "초과 권한 없음" 목록에 추가

## 5. 사용자에게 보이는 것
- 포인트 내역에 "운영자 지급 +10,000"(종류 라벨: `admin_adjust` → "운영자 지급"; 미리보기 테스트 충전도 같은 라벨)
- 이유 문구는 사용자에게 보내지 않음(관리자 기록용). 알림은 이번 범위 밖(내역과 잔액으로 확인)
- 처리방침: "회원 코드(무작위 8자리)를 만들어 마이페이지에 보여 주며, 운영자 문의·포인트 지급 때 본인 확인에 쓴다", "운영자 포인트 지급 기록(금액·이유·시각)은 탈퇴 후에도 남되 계정과의 연결은 끊는다"

## 6. 시험
- 단위: 한도(0, 100,001, 소수, 문자열 → 400), 하루 합계 경계(499,999 + 1 = 성공, + 2 = 409), 자기 자신 403, 비관리자·12시간 지난 관리자 404, 없는 코드 404, 같은 idemKey 두 번 → 한 번만
- 실제 DB(dev): 같은 관리자의 동시 지급 20건이 하루 한도를 넘지 않는지, 장부 합계 = 잔액 불변식, 탈퇴 사용자 기록 연결 끊김
- qa: 관리자 화면 흐름(코드 조회 → 확인 → 지급 → 상대 마이페이지 내역), 모바일, 오류 문구

## Security 검토 요청 사항
- 회원 코드를 식별자로 쓰는 것(길이·노출 범위·조회 제한)이 충분한지
- 관리자에게 닉네임을 보여 주는 범위
- 하루 한도의 동시성 처리(advisory lock)와 멱등 키
- 권한(0022) 목록

## Security 설계 검토 반영 (2026-10-13, 조건부 승인)
- **G-1** `admin_point_grants.entry_id`도 `ON DELETE SET NULL` — 장부 행은 사용자와 함께 지워지므로(cascade), 막혀 있으면 지급받은 사람의 탈퇴가 실패. 시험: 지급 → 탈퇴 성공 → 기록은 남고 user_id·entry_id NULL
- **G-2** 멱등은 관리자 기준: `admin_point_grants.idem_key` + UNIQUE(admin_id, idem_key)를 같은 트랜잭션에. 같은 키로 다시 오면 코드·금액이 같을 때만 처음 결과, 다르면 409. 키 형식 `^[A-Za-z0-9_-]{8,64}$`(장부 idem 제약 80자 안), 확인 대화상자마다 `crypto.randomUUID()` 한 번
- **G-3** 하나의 트랜잭션: `pg_advisory_xact_lock(hashtextextended('admin-grant:'||adminId,0))` → 오늘(KST, **DB 시각** `date_trunc('day', now() at time zone 'Asia/Seoul') at time zone 'Asia/Seoul'`) 합계 + 이번 금액 ≤ 500,000 → `credit()` → 지급 기록 INSERT. 잠금 순서: advisory → 대상 포인트 계정 하나(전체 순서 문서에 추가). dev 시험: 동시 20건이 한도를 넘지 않음
- **G-4** `gen_random_bytes`는 pgcrypto라 없음 → `upper(substr(md5(gen_random_uuid()::text), 1, 8))` + CHECK `^[0-9A-F]{8}$`
- 조회 분당 30회(관리자별), 없는 코드와 탈퇴한 코드는 같은 404. `member_code`는 api_rw가 users를 표 단위로 읽을 수 있으므로 공개·경매·알림 쿼리는 열 이름을 명시하고, 응답에 회원 코드가 없음을 시험으로 확인(A-3). 서버 로그에 닉네임·코드 금지(지급 id·금액만)
- **R-1** 관리자 계정에는 지급 불가(자기 자신 포함, 403) · **R-2** `/admin`에 최근 30일 지급 목록(시각·회원 코드·금액·이유·구분값) · **R-3** 이유는 정리(공백·제어문자 제거, 1~200자) + 이메일·전화번호 모양 거절, **1년 뒤 이유만 비움**(금액·시각은 남김) · **R-4** 실제 지급은 `ref = 'grant'`, 테스트 충전(`ref = 'test'`)은 지금처럼 미리보기 전용 · **R-5** 관리자 닉네임·구분값은 저장하지 않고 화면에서 계산 · **R-6** 대상의 동시 탈퇴는 포인트 계정 FOR UPDATE가 순서를 정함(뒤쪽이 깔끔히 실패 → 404)
- 출시: 운영 DB 0022를 **main 병합 전에**(복구 브랜치 먼저)
