# M7 가상 포인트 경매 — 설계

사용자 결정(2026-10-10)
- 경매 대상: **가상 컬렉션 카드** — 실물·배송·결제 없이, 사이트 안에서 갖는 카드(실제 카드 데이터의 한 장)를 사용자끼리 포인트로 사고판다
- 포인트 얻기: **가입 보너스 + 매일 출석 + 가상 카드 팔기**
- 실시간: SSE + 짧은 폴링으로 시작했으나, Security 검토(A-4)로 **엣지 캐시를 거친 짧은 폴링이 기본**(§5)

목표(포트폴리오): 돈처럼 다뤄야 하는 데이터를 **장부(ledger)** 로 정확하게, 경매를 **상태 머신**으로, 동시 입찰을 **트랜잭션과 잠금**으로 안전하게 처리하고 테스트로 증명한다.

## 1. 용어와 흐름

```
가입 ──▶ +10,000P (한 번)          출석 ──▶ +500P (하루 한 번, UTC가 아니라 KST 날짜)
  │
  ├─ 카드팩 열기 (1,000P) ──▶ 내 컬렉션에 카드 5장 (세트별, 희귀도 가중 추첨)
  │
  ├─ 내 카드 경매 등록 (시작가·기간) ──▶ 다른 사용자 입찰 ──▶ 마감 ──▶ 낙찰: 카드 이동 + 포인트 정산(수수료 5%)
  │                                                          └▶ 유찰: 카드 잠금 해제
  └─ 다른 사람 경매 입찰 ──▶ 입찰액만큼 포인트 "보류" ──▶ 더 높은 입찰이 오면 보류 해제
```

- 포인트는 현금 가치가 없고, 사거나 바꿀 수 없다(통신판매중개·결제 대상 아님). 화면과 약관에 명시
- 카드는 "가상 카드"이고 실물과 무관하다. 시세는 참고로만 보여 준다

## 2. 데이터 (account 스키마, `api_rw`)

### 포인트 장부
| 테이블 | 열 | 메모 |
|---|---|---|
| `point_entry` | id, user_id, amount(정수, ±), kind, ref_type, ref_id, idem_key, created_at | **추가만**(UPDATE·DELETE 권한 없음). 잔액 = 합 |
| `point_account` | user_id PK, balance, held, version | 장부 합의 캐시. `balance >= held >= 0` CHECK. 같은 트랜잭션에서 장부와 함께 갱신, 잠금 대상(FOR UPDATE) |

- kind: `signup_bonus` · `daily_bonus` · `pack_purchase` · `sale_income` · `sale_fee` · `purchase` · `admin_adjust`
- **보류(hold)** 는 장부가 아니라 `point_account.held`와 입찰 행으로 관리: 쓸 수 있는 포인트 = balance − held. 낙찰 때에만 장부에 `purchase`(−)·`sale_income`(+)·`sale_fee`(−, 판매자)를 쓴다
- `idem_key` UNIQUE(user_id, idem_key): 같은 요청 재시도로 두 번 지급·차감되지 않게(출석은 `daily:2026-10-11`, 팩은 클라이언트가 만든 요청 id)
- 매일 점검(테스트·관리 스크립트): `sum(point_entry) == point_account.balance`, held == 진행 중 경매의 내 최고 입찰 합

### 컬렉션과 카드팩
| 테이블 | 열 | 메모 |
|---|---|---|
| `owned_card` | id(uuid), user_id, card_id, acquired_at, source(`pack`/`auction`), auction_id(진행 중 경매에 잠겼으면) | 같은 카드도 한 장 한 장 별개(경매 단위) |
| `pack_opening` | id, user_id, set_id, cost, created_at | 연 기록(확률 검증·분쟁 대응) |

- 팩: 세트 하나에서 5장, 희귀도 가중(일반 3 · 언커먼 1 · 레어 이상 1, 레어 슬롯 안에서 상위 희귀도 낮은 확률). 확률표는 문서와 화면에 공개
- 추첨은 서버의 `crypto.randomInt`. 팩 세트는 스탠다드 세트 중 몇 개로 시작

### 경매와 입찰
| 테이블 | 열 | 메모 |
|---|---|---|
| `auction` | id, seller_id, owned_card_id(UNIQUE where open), card_id, start_price, min_step, status, starts_at, ends_at, original_ends_at, extensions, top_bid_id, top_amount, top_bidder_id, version, closed_at | 상태 머신(§3) |
| `bid` | id, auction_id, bidder_id, amount, created_at, idem_key | 추가만. UNIQUE(auction_id, bidder_id, idem_key) |
| `daily_claim` | user_id, day(KST) | PK — 출석 중복 방지 |

- 공개 화면에 보이는 것: 판매자 닉네임, **입찰자는 가린 닉네임**(예: 트***9, 본인에게만 전체), 입찰액, 시각. 사용자 id·OAuth 정보는 보이지 않음(A-3)
- 금액·잔액은 **bigint**, CHECK: amount ≠ 0, 시작가·최소 단위 1~1억, balance ≥ held ≥ 0, extensions ≤ 10 (A-1)
- 권한(A-1): point_entry·bid는 INSERT·SELECT만, point_account는 UPDATE(balance, held, version)만, owned_card는 UPDATE(user_id, auction_id)만, auction은 상태·top_*·ends_at·extensions·version·closed_at만 UPDATE. **DELETE 권한은 어디에도 없음**(탈퇴의 연쇄 삭제는 테이블 소유자 권한으로 FK가 처리). 서버 시작 권한 검사(필요·과다)에 새 테이블 추가
- 탈퇴(A-2): 남의 기록은 지우지 않음 — auction.seller_id·top_bidder_id, bid.bidder_id는 ON DELETE SET NULL로 "탈퇴한 사용자" 표시·금액 유지. 본인의 point_entry·owned_card는 함께 삭제

## 3. 경매 상태 머신

```
          create                       now ≥ ends_at, 입찰 있음
 (draft) ───────▶ OPEN ───────────────────────────────────────▶ SOLD
                   │  │  마감 2분 안 입찰 → ends_at = now+2분 (최대 10회)
                   │  └──────────────────────────────────────▶ UNSOLD (입찰 없음)
                   └── 판매자 취소(입찰 0건일 때만) ──────────▶ CANCELLED
```
- 허용 전이만 코드 한 곳(`transition()`)에서, DB에는 상태 CHECK + `version` 낙관적 잠금
- 마감 처리(정산)는 **HTTP 내부 주소를 만들지 않는다**(Security Q3: `api`는 누구나 호출 가능한 서비스라 IAM 보호가 없고, 프록시 인증에 구멍을 내야 함)
  - ① **지연 정산**: 결과를 보여 줄 수 있는 모든 읽기에서 — 경매 상세, `/market` 목록(그 페이지의 마감된 경매를 한 번에), 내 포인트·컬렉션 화면(내가 판매자·입찰자인 마감 경매). 참여자가 곧 볼 사람이라 "아무도 안 보는 경매"는 장부 정리만 늦어질 뿐 누구의 결과도 늦추지 않음
  - ② **매일 정리**: 기존 시세 수집 Job의 한 단계로 남은 마감 경매를 정산(전용 역할·비밀)
  - 둘이 겹쳐도 `status = 'open'` 조건부 UPDATE + 같은 잠금 순서(§4)라 한 번만 정산
- 기간: 1시간 · 24시간 · 3일 중 선택. 등록 한도: 진행 중 경매 사용자당 10개

## 4. 동시 입찰 (한 트랜잭션)

```
BEGIN
  SELECT … FROM auction WHERE id = $1 FOR UPDATE           -- 경매 행 잠금: 같은 경매 입찰은 줄을 선다
  검사: status = open, now < ends_at, bidder ≠ seller, amount ≥ max(start_price, top_amount + min_step)
  SELECT … FROM point_account WHERE user_id IN (bidder, prev_top) ORDER BY user_id FOR UPDATE
                                                             -- 항상 같은 순서로 잠가 교착 방지
  검사: bidder.balance − bidder.held (+ 이미 내가 최고 입찰자면 내 이전 보류) ≥ amount
  bidder.held += amount (자기 최고 입찰 갱신이면 차액만), prev_top.held −= prev_amount
  INSERT bid; UPDATE auction SET top_* , ends_at(연장), version+1
COMMIT
```
- 경매 행을 먼저, 그다음 사용자 행을 id 순서로 → 잠금 순서 고정. **정산도 같은 순서**(A-1: 다르면 입찰과 교착)
- 시간 판단(진행 중·마감·연장)은 모두 **DB의 now()** 로(A-1: 인스턴스 2개의 시계가 다를 수 있음)
- 수수료 = floor(낙찰가 × 5%), 테스트: 구매액 = 판매 수입 + 수수료
- 같은 요청 재시도는 idem_key로 같은 결과
- 테스트: 실제 Postgres(Neon dev 브랜치에서 일회용 브랜치)로 **동시 입찰 50건**을 Promise.all로 보내 최종 최고 입찰·보류 합·장부 합이 맞는지, 교착·이중 보류 0

## 5. 실시간 — 엣지 캐시 폴링 (Security A-4)

SSE는 열린 탭마다 요청을 8초씩 붙잡고 DB를 초당 한 번 읽게 돼, Neon이 하루 종일 깨어 있고(무료 컴퓨트 소진) 스크립트로 수백 개를 열면 비용·서비스 거부 수단이 된다. 그래서:
- `GET /api/v1/auctions/:id/state`: 공개 상태(현재가·최고 입찰자(가린 닉네임)·마감 시각·입찰 수·version)만, `ETag` + `Cache-Control: public, s-maxage=2` → 보는 사람이 많아도 CDN이 흡수, DB는 경매당 2초에 한 번 이하
- 화면은 2~3초 간격으로 폴링(탭이 안 보이면 멈춤), 마감 1분 전부터 1초
- 내 보류액·내가 최고 입찰자인지 같은 개인 정보는 별도 `no-store` 호출(입찰 직후·화면 진입 시)
- SSE는 접속이 늘면 재검토: 그때는 로그인 필수, 인스턴스당 경매별 DB 조회 1개를 연결들이 공유, 사용자·IP별 동시 연결 상한, 프록시 스트리밍 확인

## 6. 화면

- `/market` 경매 목록(마감 임박순·새로 등록·세트·가격 필터), `/auctions/:id` 상세(카드·현재가·남은 시간·입찰 기록·입찰 상자·참고 시세), `/collection` 내 카드(경매 등록), `/packs` 카드팩, 마이페이지 포인트(잔액·보류·내역)

- 카드 상세에 "이 카드 경매 N건" 링크

## 7. 보안·남용

- 모든 쓰기: 로그인 + 기존 CSRF(Origin) + 사용자별 쓰기 제한(분당 60) + 입찰은 별도로 분당 20
- 금액은 정수 포인트, 상한 1억P, 입력은 zod로 정수·범위
- 다중 계정(구글+카카오로 보너스 두 번)·자전 입찰은 가상 포인트라 받아들임 — 문서화. 단, 같은 사용자의 자기 경매 입찰은 막음
- 관리자 조정(`admin_adjust`)은 소유자 스크립트로만, API 없음
- 탈퇴: 진행 중 경매 판매자·최고 입찰자면 막고 안내(경매 종료 후 가능), 나머지는 §2(A-2)
- **닉네임 공개 대비(A-3, 7c 전에)**: 예약어(운영자·관리자·admin·system·official·포켓몬 공식…), NFKC 정규화 + 섞인 문자 유사 글자 차단, 정규화 기준 중복 금지, 닉네임 변경 쿨다운(경매 중 판매자 이름 가로채기 방지)
- 약관: "포인트·카드는 현금 가치가 없고, 돈을 받고 포인트·카드·계정을 거래하는 것(RMT)은 금지". 포인트는 **절대 판매하지 않음**(게임·전자금융 규제 대상이 됨)
- 개인정보처리방침: 포인트·컬렉션·입찰·팩 기록, 보관(탈퇴 시 삭제, 남의 거래 상대 기록은 익명으로 유지), 공개 항목(가린 닉네임·금액·시각)
- 다중 계정 보너스·자전 입찰은 가상 포인트라 감수(문서화), 취소 시도 횟수 제한
- 팩: 확률을 서버 상수로, 10만 번 추첨 통계 테스트(허용 오차 안), 팩 구매 장부와 뽑은 카드를 한 트랜잭션 + idem_key

## 9. 화면 상태·문구 (qa 설계 검토, 2026-10-10)

**경매 상세**
- 시간은 **서버 시계 기준**: 모든 경매 응답에 `serverNow`를 넣고 기기 시계와의 차이를 보정해 카운트다운(기기 시계가 30초 틀려도 맞게). 숫자는 tabular-nums·고정 폭(매초 줄바꿈·밀림 방지)
- 0초가 되면 입력을 막고 "마감 처리 중…" → 결과로 교체: 낙찰 "망나뇽님이 8,400P에 낙찰받았어요" / 입찰 없음 "입찰 없이 끝났어요"(유찰이라는 말은 쓰지 않음) / 취소
- 역할별: 낙찰자 "낙찰! 내 컬렉션에 추가됐어요"(링크), 판매자 "판매됨 +7,980P (수수료 420P)", 밀린 사람 "보류한 8,200P가 돌아왔어요"
- 연장: "마감이 2분 늘었어요 (3/10)"를 한 번(스크린 리더 polite 알림, 매초 읽지 않음), 10/10이면 "더 이상 연장되지 않아요". 문구 "마감 2분 전부터 입찰이 들어오면 2분 늘어나요"
- 제출 사이에 다른 입찰: 서버 거절 → "방금 8,600P 입찰이 들어왔어요. 최소 8,700P부터 가능해요", 새 최소가를 채우고 입력에 포커스(지우지 않음)
- 이미 최고 입찰자: "현재 최고 입찰자예요", 올리면 "내 입찰을 9,000P로 올려요 (추가로 600P 보류)"
- 포인트 부족: 입력 중에 쓸 수 있는 포인트와 비교해 "1,200P 부족해요" + 출석·내 카드 팔기 링크(버튼만 흐리게 두지 않음)
- 내 경매: 입찰 상자 대신 판매자 패널(현재가·입찰 수, 입찰 0건일 때만 취소, 아니면 "입찰이 있어 취소할 수 없어요")
- 로그아웃: 입찰 상자 자리에 "로그인하고 입찰하기"(next=/auctions/:id). `/market`·경매 상세는 누구나, `/collection`·`/packs`는 로그인 페이지로
- 중복 제출: 처리 중 버튼 잠금, 네트워크 오류 재시도는 **같은 idem_key**(출석·팩도 같음). 429는 Retry-After로 "N초 뒤 다시 입찰할 수 있어요"
- 휴대폰: 입찰 상자는 화면 아래 고정 막대(현재가·남은 시간·입력·입찰), `inputmode="numeric"` + 입력 중 천 단위 쉼표, "+100"·"최소가" 버튼
- 실시간 표시: "실시간" 배지 대신 실제 상태 — "2초마다 확인" / "다시 연결 중…"

**목록·컬렉션·팩·출석·장부**
- `/market`: 로딩 스켈레톤은 고정 높이(시세 탭 교훈), 경매 없음 "진행 중인 경매가 없어요" + 등록 버튼, 필터 결과 없음은 다른 문구, 오류 + 다시 시도. 마감된 경매는 다음 새로고침까지 "마감" 표시로 남음(보는 중에 칸이 사라져 밀리지 않게). 360px 2열, 긴 이름 말줄임, 가격·시간 줄 고정 높이
- 출석: "출석 체크 +500P" → 받은 뒤 "오늘 출석 완료". KST 자정 경계, 다른 기기에서 이미 받았으면 조용히 숨김, "+500P" 알림과 헤더 잔액 갱신
- 팩: 포인트 부족, 움직임 줄이기(prefers-reduced-motion) 설정이면 애니메이션 없이, 5장을 목록으로 읽어 줌, **차감 후 연결이 끊겨도 다시 열면 마지막 팩 결과를 보여 줌**(1,000P 잃었다고 생각하지 않게). 320px는 2~3열
- 컬렉션: 경매 중인 카드는 "경매 중"(그 경매로 링크), 중복 등록 불가. "덱과 컬렉션은 별개예요"(카드를 팔아도 덱에서 빠지지 않음)
- 장부: 페이지 나눔, KST 날짜, 진짜 빼기 기호(−)와 tabular-nums, "입찰 보류(묶인 포인트)" 첫 등장 설명, 수수료 반올림 규칙 표기("5%에서 1P 미만은 버려요")
- 탈퇴가 막힐 때: 이유와 해당 경매 목록
- 헤더: 휴대폰(≤640)에서는 포인트·출석을 계정 메뉴 안으로(내비 4개 유지). **360·320 시안을 7a 전에 만든다**
- "포인트는 현금 가치가 없고, 사거나 바꿀 수 없어요"

## 10. qa용 장치 (미리보기·dev 전용, 테스트 로그인과 같은 이중 잠금: APP_ENV=preview + dev_marker, 운영에서는 시작 거부)

- 짧은 기간(2분·5분)과 연장 창·폭 설정(예: 20초 창, +20초)
- `POST /api/v1/test/auctions/:id/ends-in {seconds}`(본인·테스트 경매만), `POST /api/v1/test/auctions/settle`(실제 정산과 같은 코드)
- `POST /api/v1/test/points {amount}`(admin_adjust), `POST /api/v1/test/cards {cardId, count}`(source 'test')
- 팩 추첨 시드(`?seed=`)와 확률 덤프, `GET /api/v1/test/ledger-check`(장부 합·잔액·보류 불일치 목록)
- 강제 폴링 플래그, 모든 경매 응답의 `serverNow`
- 동시 입찰 50건 스크립트를 저장소에 두고 qa가 미리보기에 재실행할 수 있게
- 이 장치들은 Security 검토 대상(테스트 로그인과 같은 기준)

### 엣지 캐시·지연 정산이 만드는 경계 (qa, 7c 전에 확정)
1. **시계 보정**은 캐시되지 않은 응답(`no-store`: 개인 상태 호출·입찰 응답)의 `serverNow`로만 계산. 캐시된 공개 상태의 `serverNow`는 쓰지 않음(최대 2초 이상 늦을 수 있음)
2. **버전은 뒤로 가지 않음**: 입찰하면 입찰 응답으로 바로 그리고, 그 응답의 `version`보다 낮은 폴링 결과는 버림(캐시된 옛 상태로 가격이 되돌아가거나 "밀렸어요"가 잘못 뜨지 않게)
3. **마감 시각이 지나면 상태와 상관없이 끝난 것으로**:
   - (a) 모든 화면은 `now ≥ ends_at`이면 끝난 것으로 표시("마감 처리 중…" 또는 계산된 결과)
   - (b) 내 컬렉션·포인트 내역·마이페이지를 읽을 때, 내가 판매자이거나 최고 입찰자인 마감 경매를 같은 요청에서 정산
   - (c) ledger-check: 마감됐지만 아직 정산 안 된 경매의 최고 입찰은 **보류에 포함**(정산 전까지 실제로 묶여 있음), 결과 목록에 "정산 대기 N건"으로 따로 표시해 불일치로 세지 않음
4. **닉네임 규칙 하나**: 공개되는 모든 곳(입찰 기록·결과 문구·목록)은 판매자 이름만 그대로, 입찰자·낙찰자는 가림(트***9). 본인은 "피카츄 (나)". 예) "트***9님이 8,400P에 낙찰받았어요", 낙찰자 본인에게는 "낙찰! 내 컬렉션에 추가됐어요"
