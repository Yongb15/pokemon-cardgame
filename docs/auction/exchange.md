# 10팩 열기 · 중복 카드 교환 · 카드 만들기 — 설계 (v1.16.0)

사용자 요청(2026-10-21): 포인트를 쓸 곳이 카드팩(1팩 1,000P)뿐이다. 10팩을 한 번에 열고 싶다. 중복 카드를 교환하고 싶다.

지금 포인트 흐름: 들어오는 것은 가입 10,000P, 출석 500P/일, 경매 판매. 사라지는 것은 카드팩과 경매 수수료 5%뿐이다(경매 대금은 사용자끼리 옮겨질 뿐).

## 1. 10팩 한 번에 열기
- `POST /api/v1/me/packs { setId, idemKey, count }`: `count`는 1(기본) 또는 10만 허용하고, 그 밖은 400.
  - 10팩 = **10,000P**(할인 없음). 대신 **보장**이 있다: 10팩 중 **1장 이상 울트라 레어 이상**(ultra·sir·hyper).
  - 보장 방식: 1~9팩을 보통대로 뽑고, 그중 울트라 이상이 없으면 **10번째 팩의 레어 칸만** 울트라 이상 비율로 다시 정한 가중치(ultra 6 : sir 3 : hyper 1, 세트에 없는 등급은 빼고 비례)로 뽑는다.
  - 보장 없이도 10팩에 울트라 이상이 나올 확률은 약 65%다. 나머지 35%에서만 10번째 팩이 보장으로 바뀐다.
  - 확률 공개(K-1): `/packs` 화면과 `GET /api/v1/packs`에 보장 규칙과 10번째 팩 보장 가중치를 함께 싣는다(보여 주는 것 = 뽑는 것).
- 기록
  - `pack_openings` 10줄: 팩마다 하나, idem `키-0`~`키-9`. 그래서 요청 idemKey는 8~60자로 제한한다.
  - 장부 `pack_purchase` 10줄(−1,000P씩, idem `pack:키-i`)
  - `owned_cards` 50줄
  - **모두 한 트랜잭션**: 하나라도 실패하면 포인트도 카드도 없다.
- 멱등: `키-0`이 이미 있으면 그 묶음 10팩을 그대로 돌려준다(다시 과금하지 않음). 개수가 다르면(1팩 요청에 묶음 키) 409.
- 잠금 순서: 포인트 계정 하나(기존 1팩과 같음). 잔액이 10,000P보다 적으면 422.
- 화면(`/packs`)
  - [1팩 열기 1,000P] [10팩 열기 10,000P] 버튼, 보장 안내 문구
  - 결과: 50장을 등급 높은 순으로 보여 준다(새 카드 표시, 보장으로 나온 카드에는 "보장" 표시)

## 2. 중복 카드 교환 (카드 → 포인트)
- **남는 장만** 교환한다: 카드마다 최소 1장은 남긴다. 경매에 올린 장(`auction_id` 있음)과 테스트 장(`source = 'test'`)은 교환할 수 없다.
- 교환 값(등급별, 카드팩 풀의 등급 기준)

| 등급 | 교환 | 만들기 |
|---|---|---|
| 커먼 | 10P | 100P |
| 언커먼 | 20P | 200P |
| 레어 | 100P | 1,000P |
| 더블 레어 | 200P | 2,000P |
| 일러스트 레어 | 300P | 3,000P |
| 울트라 레어 | 500P | 5,000P |
| SIR | 1,500P | 15,000P |
| 하이퍼 레어 | 3,000P | 30,000P |

  - 교환 값은 만들기 값의 1/10이다(교환 → 만들기를 반복해 포인트를 늘릴 수 없음).
  - 카드팩 1팩을 모두 교환하면 기대값은 약 290P(29%), 10팩(보장 포함)은 약 3,190P(32%)다. 포인트가 계속 줄어드는 구조다(단위 시험으로 40% 이하를 고정).
- `POST /api/v1/me/cards/exchange { cardId, count, idemKey }` → `{ exchanged, points }`
  - `count`는 1 이상, (교환 가능한 장수 − 남길 1장) 이하. 넘으면 409로 지금 가능한 장수를 돌려준다.
  - 장부 `card_exchange`(+), ref = 카드 id, idem `exchange:키`
- **카드를 지우는 방법(권한)**
  - 지금 `api_rw`는 `owned_cards`를 DELETE할 수 없다(초과 권한 목록). 이 원칙은 유지한다.
  - **제안**: 소유자 권한으로 만든 DB 함수 `account.exchange_cards(user_id, card_id, n)`(SECURITY DEFINER, `search_path` 고정)
    - 하는 일은 하나뿐이다: 그 사용자의 그 카드 중 `auction_id is null and source <> 'test'`인 장을 오래된 것부터 n장 지운다(FOR UPDATE).
    - 남는 장이 1장 미만이 되면 예외를 내고, 지운 장수를 돌려준다.
    - `api_rw`에는 이 함수의 EXECUTE만 준다.
  - 앱은 같은 트랜잭션에서 계정 잠금 → 함수 호출 → 장부 기록 순으로 한다.
  - 다른 방법(`exchanged_at` 열 + 모든 조회에 조건 추가)은 조회 25곳을 고쳐야 해서 빠뜨릴 위험이 크다.
- 경매와 겹칠 때: 경매 등록·입찰은 카드 행을 잠근다. 함수도 FOR UPDATE로 잠그므로 동시에 같은 장을 쓰지 못한다(잠금 순서: 포인트 계정 → 카드).

## 3. 카드 만들기 (포인트 → 카드)
- 카드팩 풀에 있는 카드만 만들 수 있고, 값은 위 표를 따른다. `owned_cards`에 `source = 'craft'`로 1장을 넣는다(INSERT 권한은 이미 있음).
- `POST /api/v1/me/cards/craft { cardId, idemKey }` → `{ cardId, points }`
  - 장부 `card_craft`(−), ref = 카드 id, idem `craft:키`
  - 잔액이 모자라면 422. 하루 만들기 횟수 상한은 20장(실수 방지·남용 방지).
- 화면: 컬렉션의 "아직 못 모은 카드" 목록 옆에 [만들기 1,000P] 버튼. 확인 대화상자를 거친다.

## 4. 화면 (컬렉션)
- 카드마다 보유 장수가 2장 이상이면 [교환] 버튼을 단다. 장수를 고르면 "+20P × 3 = 60P" 미리보기 → 확인.
- "남는 카드 한 번에 교환"(전체 일괄)은 이번 범위에서 뺀다. 실수했을 때 되돌릴 수 없어서다.
- 포인트 내역 라벨: `card_exchange` → "카드 교환", `card_craft` → "카드 만들기"

## 5. 데이터 (마이그레이션 0024)
- `point_entries.kind` CHECK에 `card_exchange`, `card_craft` 추가
- `owned_cards.source` CHECK에 `craft` 추가
- `pack_openings`: 묶음 표시 열 `bundle_idx smallint null`(0~9)
- 함수 `account.exchange_cards`(소유자, SECURITY DEFINER), `api_rw` EXECUTE
- 권한 검사 목록: EXECUTE를 확인하는 항목 추가, DELETE는 여전히 초과 권한
- 운영 적용: 복구 브랜치 → 0024 → **병합 전에**(권한·함수가 생기므로)

## 6. 시험
- 단위
  - count 1/10만, 10팩 과금 10,000P와 50장
  - 보장(울트라 이상이 없을 때만 10번째 레어 칸 교체, 시드로 재현)
  - 같은 키 재요청은 같은 10팩, 1팩↔10팩 키 충돌은 409
  - 교환: 남길 1장, 경매·테스트 장 제외, 값 표
  - 만들기: 풀 밖 카드 404, 잔액 부족 422, 하루 20장
- 실제 DB(dev)
  - 10팩 동시 요청 20건: 잔액 음수 없음, 장부 합계 = 잔액
  - 교환 × 경매 등록 경합: 같은 장이 둘 다 되지 않음
  - 함수가 경매 장·테스트 장·마지막 1장을 지우지 않음
  - api_rw로 DELETE 직접 실행은 거절됨
- qa: 10팩 결과 화면(50장, 모바일), 교환·만들기 흐름, 포인트 내역 라벨, 회귀

## Security 검토 요청 사항
- SECURITY DEFINER 함수 방식(범위, search_path, 권한)이 "api_rw DELETE 금지" 원칙을 지키는지
- 10팩 보장의 확률 공개 방식(K-1)
- 교환 값과 만들기 값의 비율(포인트가 늘어나는 순환이 없는지)
- 하루 만들기 상한, 쓰기 요청 제한

## Security 설계 검토 반영 (2026-10-21, 조건부 승인)
- **X-1** 함수의 기본 EXECUTE(PUBLIC)를 REVOKE하고 api_rw에만 GRANT한다. 시작 검사(`exchangeFunctionCheck`)로 PUBLIC·collector_rw·app_rw에 실행 권한이 없음을 확인한다
- **X-2** 함수 소유자는 로그인할 수 없는 `card_exchanger`다. 권한은 owned_cards SELECT·DELETE, auctions SELECT, account 스키마 USAGE뿐이다. 소유자를 바꿀 때만 CREATE를 잠깐 주고 바로 회수한다. 초과 권한도 시작 검사로 확인한다
- **X-3** `SET search_path = pg_catalog, pg_temp`, 모든 객체 이름에 스키마를 붙이고 동적 SQL은 쓰지 않는다. 함수 안에서 n 1~50, user_id, 카드 id 형식, 테스트·경매 장 제외, 1장 남기기를 직접 검사한다
  - 구현 중 변경: `SELECT … FOR UPDATE`는 UPDATE 권한이 있어야 해서(권한 거부로 확인됨), 소유자에게 UPDATE를 주는 대신 **DELETE가 행을 잠그고 조건을 다시 확인**하게 했다
  - 지운 장수가 n보다 적거나 남는 장이 없으면 예외를 낸다(호출한 트랜잭션 전체를 되돌림). 경매 등록이 먼저 잡은 장은 DELETE가 기다린 뒤 다시 확인해서 건너뛴다
- **X-4** 잠금 순서: 포인트 계정 → 함수(카드 장).
  - 경매 등록은 `FOR UPDATE SKIP LOCKED`로 장을 잡아서, 두 작업이 같은 장을 함께 쓰지 못한다. dev에서 경합 10회를 돌려 0장이 되거나 경매 장이 지워진 경우가 없음을 확인했다
  - 지난 경매로 산 장을 교환하면 그 경매의 `owned_card_id`가 NULL이 된다(경매 기록은 card_id를 그대로 가짐)
- **X-5** 10팩의 행 10개는 같은 idem_key를 쓰고 bundle_idx 0~9로 구분한다. UNIQUE는 (user_id, idem_key, bundle_idx)다. 같은 키로 개수가 다르면 409이고, 단일 "x-3"과 묶음 "x" 서로 겹치지 않음을 시험했다
- **X-6** 기대 교환값을 단위 시험에 고정했다. 처음 값표(울트라 1,000 · SIR 3,000 · 하이퍼 5,000)로는 10팩 보장 포함 44.7%가 나와 시험이 실패했다 → 500 · 1,500 · 3,000으로 내렸다(만들기 값도 함께)
- **X-7** 교환은 한 번에 50장, 하루 50,000P(DB 시각, `exchange:`+사용자 advisory lock), 만들기는 하루 20장(`craft:`+사용자 lock), 쓰기 요청은 분당 20회
- **X-8** 보장 규칙과 가중치를 데이터로 공개한다(같은 상수에서 계산, 시험). 1팩에는 보장이 없다고 밝힌다
- **X-9** 약관에 교환·만들기와 되돌릴 수 없음을 적었다(시행일 2026-10-21). 확인 대화상자에 장수와 포인트를 보여 준다
- dev 점검: `apps/api/scripts/db-check-exchange.ts`(36항목)
