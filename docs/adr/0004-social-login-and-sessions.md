# ADR 0004 — 소셜 로그인과 서버 세션

- 상태: 채택 (2026-10-08)
- 관련: M6

## 결정

1. **구글·카카오 로그인만** (사용자 결정)
   - 비밀번호를 저장하지 않는다 → 유출·재설정·무차별 대입 걱정이 없다
   - 이메일 발송(인증·비밀번호 찾기)이 필요 없다 → 자체 도메인 없이 가능
   - 이메일·비밀번호 가입은 도메인을 갖춘 뒤 별도 결정
2. **OAuth 2.0 Authorization Code + PKCE, OpenID Connect**
   - `state`(CSRF)·`nonce`(재전송)·PKCE 검증값은 짧게 사는 httpOnly 쿠키에 담고 콜백에서 대조
   - 서버가 code를 교환하고 **id_token 서명(JWKS)·발급자·대상·만료·nonce를 검증**한 뒤 `sub`(제공자 사용자 id)로 계정을 찾는다
   - 카카오도 OpenID Connect를 켜서 같은 방식으로 검증
3. **세션은 DB에 두는 불투명 토큰** (JWT 아님)
   - 로그인 시 32바이트 난수 → 쿠키 `__Host-session`(Secure, HttpOnly, SameSite=Lax, Path=/), DB에는 **SHA-256 해시만** 저장
   - 30일, 사용하면 연장(슬라이딩). 로그아웃·"모든 기기에서 로그아웃"·탈퇴 시 즉시 무효 — JWT와 달리 바로 끊을 수 있다
   - 로그인할 때마다 새 토큰(세션 고정 공격 방지)
4. **CSRF**: SameSite=Lax + 상태를 바꾸는 요청은 `Origin`이 우리 사이트이고 `Content-Type: application/json`일 때만 처리
5. **최소 수집**: 제공자·`sub`·닉네임만. 이메일·프로필 사진·전화번호는 받지 않는다(동의 항목 최소화). 같은 사람이 구글·카카오로 따로 들어오면 **자동으로 합치지 않는다**(이메일로 묶으면 계정 탈취 경로가 될 수 있음).
6. **탈퇴하면 즉시 삭제**(덱·관심 카드·세션 포함). 개인정보처리방침·이용약관 페이지를 둔다.

## 대안

| 대안 | 제외 이유 |
|---|---|
| JWT(Access/Refresh) | 즉시 무효화가 어렵고, 같은 출처라 쿠키 세션이 더 단순·안전 |
| Auth.js / Lucia 등 라이브러리 | 학습·포트폴리오 목적상 흐름을 직접 구현(검증은 `jose` 라이브러리 사용) |
| 이메일 자동 계정 병합 | 제공자별 이메일 검증 수준이 달라 탈취 위험 |
