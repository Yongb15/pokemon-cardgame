# ADR 0005 — 포인트 장부와 경매 동시성

- 상태: 채택 (2026-10-10, Security 설계 검토 A-1~A-4 반영)
- 관련: M7 가상 포인트 경매 (docs/auction/design.md)

## 배경

가상 포인트지만 "돈처럼" 다룬다: 잃어버리거나 두 번 지급되면 안 되고, 여러 명이 같은 순간 입찰해도 결과가 하나로 정해져야 한다. 서버는 Cloud Run 최대 2개 인스턴스, DB는 Neon Postgres(api_rw, pg Pool, 트랜잭션 사용 가능).

## 결정

1. **추가만 하는 장부 + 잔액 캐시**
   - `point_entry`는 INSERT만(UPDATE·DELETE 권한을 주지 않음). 모든 변동은 kind·참조(경매·팩)·idem_key와 함께 한 줄
   - `point_account(balance, held)`는 같은 트랜잭션에서 갱신하는 캐시이자 잠금 대상. `balance >= held >= 0` CHECK로 음수 잔액은 DB가 거부
   - 정합성 점검: 장부 합 = balance, held = 진행 중 경매의 최고 입찰 합 (테스트·점검 스크립트)
2. **입찰 보류는 장부가 아니라 held로**: 밀릴 때마다 장부 두 줄(보류·해제)이 쌓이지 않게. 장부에는 실제로 주인이 바뀌는 순간(낙찰 정산)만
3. **비관적 잠금(SELECT … FOR UPDATE)** 을 입찰 트랜잭션에: 경매 행 → 관련 사용자 행(id 순). 경합이 한 경매에 몰리고 트랜잭션이 짧아 줄 세우기가 가장 단순하고 확실. 상태 전이는 `version` + 조건부 UPDATE(낙관적)로 정산 중복을 막음
4. **멱등성**: 쓰기 요청마다 클라이언트 요청 id(idem_key), DB UNIQUE
5. **마감 정산은 지연 + 매일**: 결과를 보여 줄 읽기에서 그 자리에서 정산하고, 시세 수집 Job의 한 단계로 남은 것을 정리. **HTTP 내부 주소 없음**(`api`는 공개 호출 서비스라 IAM 보호가 없고 프록시 인증에 예외가 생김 — Security Q3). 시간 판단은 DB now()
6. **실시간은 엣지 캐시 폴링**(공개 상태 s-maxage=2 + ETag, 개인 정보는 no-store 별도): SSE는 탭마다 요청·DB 조회를 붙잡아 비용·서비스 거부 수단이 됨(Security A-4). WebSocket은 Cloud Run 요청 시간·무료 한도 위험

## 대안

- 잔액만 두고 UPDATE(장부 없음): 단순하지만 "왜 이 잔액인가"를 설명할 수 없고 버그를 되돌릴 수 없음
- 낙관적 잠금만으로 입찰: 경합 때 재시도가 몰려 같은 경매 마감 직전에 실패율이 큼
- Redis·큐 기반 입찰: 정확하지만 인프라·비용 추가, 포트폴리오 규모에 과함
- WebSocket: ADR 0003에서 예정했지만 비용·10초 제한 때문에 보류(동시 접속이 늘면 재검토)

## 결과

- 동시 입찰·정산 정확성은 실제 Postgres에 동시 요청을 보내는 통합 테스트로 확인한다(일회용 Neon 브랜치)
- 장부 테이블은 계속 커진다: 사용자당 하루 몇 줄 수준이라 무료 0.5GB 안에서 수년
