# v1.17.0 설계 — E2E 테스트 자동화 · 설계 문서 정리

사용자 결정(2026-10-24): 포켓몬 프로젝트의 마지막 큰 출시. 지금까지 화면 검증은 qa 세션이 사람처럼 직접 했다. 핵심 흐름을 **자동 E2E 테스트**로 만들어 CI에서 매번 돌리고, 면접에서 보여 줄 수 있게 **설계 문서**(ERD·권한·잠금 순서·결정 기록)를 한 곳에 모은다.

## 1. E2E 테스트 (Playwright, Chromium)
`e2e/` 폴더, 설정 `playwright.config.ts`. 두 묶음으로 나눈다. 로그인은 미리보기의 테스트 로그인(test provider)에서만 되기 때문이다.

### 1a. 공개 흐름 — 모든 push·PR의 CI에서
- 대상: CI 안에서 띄운 `vite` 개발 서버(카드 API는 저장소의 데이터 파일로 응답)
  - 시세·계정 API는 없으므로 그 화면은 "불러오지 못함" 상태가 정상이다
- 흐름
  1. 한국어 검색("리자몽") → 결과 → 카드 상세(이름·기술·"← …에서 진화" 링크 → 정확 일치가 먼저)
  2. 세트 페이지(`/?set=sv3pt5`) 번호순
  3. 덱 빌더
     - 카드 담기, 4장 제한, 규칙 검사 문구
     - PTCG Live 내보내기 텍스트
     - 공유 링크 → 공유 화면(h1 → h2 → h3)
  4. 덱 시뮬레이터: 60장 가져오기 → 섞고 시작(패 7장·프라이즈 6장) → 1장 뽑기
  5. 없는 주소 → 404 화면
  6. 375px·다크 모드에서 목록·상세가 가로로 넘치지 않음
- 공통 검사: 콘솔 오류 0개(계정·시세 API 실패처럼 예상된 것은 허용 목록)
- 시간: 2~3분. 실패하면 스크린샷만 산출물로 올린다(추적 파일은 올리지 않음, §3)

### 1b. 계정 흐름 — develop 배포 뒤 미리보기에서
- 대상: `https://pokemon-card-dex-git-develop-dydqls-projects.vercel.app`(dev DB, 테스트 로그인 켜짐)
- 실행 시점: `Deploy API` 워크플로가 develop에서 성공한 뒤(`workflow_run`) + 수동 실행. 한 번에 하나만(concurrency)
- 계정: 실행마다 새 테스트 계정 2개(`e2e-<run id>-a`, `-b`). 끝나면 **항상** 탈퇴 API로 지운다(실패해도 `finally`)
- 흐름
  1. 테스트 로그인 → 마이페이지(닉네임·회원 코드·판매자 배지)
  2. 출석 체크 → 포인트 +500
  3. 1팩 열기 → 5장, 10팩 열기 → 50장·울트라 이상 1장 이상
     - 포인트는 테스트 지급 훅(미리보기·테스트 계정 전용)으로 채운다
  4. 컬렉션: 세트 수집 현황, 교환(1장 남김) → 포인트 증가, 만들기 → 카드 추가
  5. 덱 저장 → 다시 열기(계정 동기화)
  6. 경매: A가 카드 등록 → B가 입찰 → A가 더 높게 못 함(본인) → B가 밀리는 경우는 C 없이 A의 두 번째 경매로 대신 → 알림 종에 "밀림" 1개
  7. 장부 확인: 화면의 포인트 내역 합계 = 잔액
- 운영 사이트·운영 DB는 건드리지 않는다. 비밀값은 필요 없다(테스트 로그인은 미리보기의 dev DB에서만 열리고, 정식 사이트에서는 이중으로 막혀 있음)

### 1c. CI 구성
- `ci.yml`의 `check` 작업 뒤에 `e2e-public` 작업: `npx playwright install --with-deps chromium` → `npm run e2e:public`
- 새 `e2e-preview.yml`: `on: workflow_run (Deploy API, develop, success)` + `workflow_dispatch`
  - 권한은 `contents: read`만, 비밀값 없음
  - `npm run e2e:account`, 실패하면 스크린샷 산출물(7일 보관)
- main에는 영향 없음(정식 사이트 대상 E2E는 만들지 않음: qa의 운영 회귀가 그 역할)

## 2. 설계 문서
- `docs/architecture.md`(새 파일): 한 문서로 전체를 설명한다
  1. 구성도(README의 Mermaid 재사용)
  2. **ERD**(Mermaid `erDiagram`): account 스키마 20개 표와 public의 시세 표, 주요 FK·UNIQUE
  3. **DB 계정과 권한 표**: app_rw · api_rw · collector_rw · card_exchanger 각각 할 수 있는 것과 없는 것, 시작 시 권한 검사
  4. **잠금 순서**: 경매 → 포인트 계정(id 순) → 카드 → 알림, advisory lock(관리자 지급·교환·만들기)
  5. 요청 흐름: 브라우저 → Vercel(정적·카드/시세 함수·middleware 프록시) → Cloud Run API → Neon

  7. 테스트 피라미드: 단위(vitest) · dev DB 점검 스크립트 · E2E · qa 수동 · Security 검토

  - `0007-privileged-functions.md`(SECURITY DEFINER로 삭제 권한 감싸기)

## 3. 안전·비용
- E2E가 만드는 데이터는 dev DB의 테스트 계정뿐이고, 실행마다 지운다. 남은 계정은 이름 패턴(`e2e-`)으로 정리할 수 있다
- 실패 산출물은 스크린샷만 올린다
  - Playwright 추적 파일(trace)에는 요청 헤더·쿠키가 들어가므로 올리지 않는다. 테스트 계정의 세션이라도 올리지 않는다
- GitHub Actions 무료 시간: 공개 2~3분/푸시, 계정 4~5분/develop 배포 → 무료 한도 안
- 미리보기 요청량: 실행당 수십 건(분당 제한 안에서 흐름 사이에 대기)

## 4. 시험
- E2E 자체를 처음 만들 때: 일부러 깨뜨린 화면(예: 덱 4장 제한 문구 바꾸기)에서 실패하는지 확인
- qa: 테스트 목록이 지금까지의 qa 회귀 항목과 겹치는지, 빠진 핵심 흐름이 없는지 검토

## Security 검토 요청 사항
- `workflow_run`으로 미리보기에 테스트 로그인을 쓰는 방식(정식 사이트에는 열 수 없음 확인), 권한·비밀값 없음
- 실패 산출물 범위(스크린샷만)
- 테스트 계정 정리 방식
